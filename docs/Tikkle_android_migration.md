## 1. 🔴 제거된 응답 필드

### 1-1. `isUpbitKeyValid` — 2곳에서 제거

**`GET /api/users/me`**
```diff
  {
    "hasInvestmentProfile": true,
    "hasKbankAccount": true,
    "hasUpbitKey": true,
-   "isUpbitKeyValid": true      // ❌ 제거됨
  }
```

**`GET /api/settings`**
```diff
  "linkedAccount": {
    "targetCardCompany": "KBANK",
    "targetCardLast4": "1234",
    "twoFactorProvider": "KAKAO",
-   "isUpbitKeyValid": true      // ❌ 제거됨
  }
```

**왜 없어졌나요?** 서버가 업비트 키의 유효성을 **별도 필드로 보관하지 않게** 바뀌었습니다. 키 검증은 **등록/수정 시점에만** 수행하고, 이후의 만료·권한 회수는 실제 업비트 API를 호출할 때 401로 감지합니다. 보관하지 않으니 응답에 담을 값도 없습니다.

**그럼 어떻게 판단하나요?** → **`UPBIT-010` 에러로 판단**하시면 됩니다.

| 시점 | 엔드포인트 | 키가 죽었으면 |
| --- | --- | --- |
| **홈/포트폴리오 진입** (주 감지 지점) | `GET /api/upbit/portfolios` | `401` + `UPBIT-010` |
| 매수 승인 | `POST /api/payments/{eventId}/approve` | `401` + `UPBIT-010` |

```json
{
  "code": "UPBIT-010",
  "message": "유효하지 않거나 권한이 부족한 업비트 API 키입니다."
}
```

기존에 `isUpbitKeyValid == false`로 하던 분기를 여기로 옮기시면 **동일한 UX**가 나옵니다. 오히려 실시간이라 더 정확합니다.

> `hasUpbitKey`(연동 여부)는 **그대로 유지**됩니다. "아직 연동 안 함" 분기는 계속 이 값을 쓰세요.
> 즉 **`hasUpbitKey: false` → "연동해주세요"**, **`hasUpbitKey: true` + `UPBIT-010` → "재연동해주세요"** 로 구분됩니다.

### 1-2. `status` — `GET /api/users/me`에서 제거

```diff
  {
    "id": 1,
    "name": "홍길동",
    "phoneNumber": "01012345678",
-   "status": "ACTIVE",          // ❌ 제거됨
    "createdAt": "2024-01-01T00:00:00",
    ...
  }
```

회원 탈퇴가 완전 삭제로 바뀌면서 **계정 상태 개념 자체가 사라졌습니다**(§5 참고). 조회되는 유저는 항상 활성이므로 이 필드는 언제나 `"ACTIVE"`만 반환하던 무의미한 값이었습니다.

## 2. ⚠️ 가장 중요 — 401 인터셉터 주의

**`UPBIT-010`은 401이지만 인증 실패가 아닙니다.**

공통 인터셉터가 "401 → 토큰 갱신 / 로그아웃"으로 처리하고 있다면, 업비트 키가 만료된 유저가 **로그아웃당하는 버그**가 생깁니다.

👉 **HTTP 상태가 아니라 `code` 값으로 분기**해주세요.

| code | 처리 |
| --- | --- |
| `AUTH-001` / `AUTH-002` / `AUTH-003` / `AUTH-006` | 토큰 갱신 또는 로그아웃 |
| `UPBIT-010` | **로그아웃 금지.** 업비트 재연동 안내 |

## 3. 🟢 비밀번호 재설정 — 이제 실제로 동작합니다

**기존에는 호출 자체가 불가능했습니다.** 3개 엔드포인트가 시큐리티 설정에서 인증 예외로 등록되지 않아 JWT를 요구했는데, 비밀번호를 잊은 사용자는 JWT가 없으니 논리적으로 도달할 수 없는 API였습니다. 이번에 **Public으로 수정**되어 정상 동작합니다.

### 흐름
```
1. POST /api/auth/password/reset-sms/send     { phoneNumber }
      → 200 (인증번호 발송)
2. POST /api/auth/password/reset-sms/verify   { phoneNumber, code }
      → 200 { "token": "uuid..." }            ← resetToken (30분 유효, 1회용)
3. POST /api/auth/password/reset              { phoneNumber, newPassword, resetToken }
      → 200
```

### ⚠️ 1번은 미가입 번호여도 200을 반환합니다
사용자 열거(가입 여부 확인) 공격을 막기 위한 의도된 동작입니다. **"가입되지 않은 번호입니다" 같은 화면을 띄우면 안 됩니다.** 미가입/가입 모두 "인증번호를 발송했습니다"로 안내하고 다음 단계로 진행시켜 주세요. (미가입이면 2번에서 `SMS-002`로 걸립니다.)

### ⚠️ 3번 성공 시 기존 세션이 끊깁니다
비밀번호 재설정에 성공하면 서버가 해당 유저의 **refreshToken을 삭제**합니다. 계정 탈취 시 공격자를 즉시 축출하기 위한 조치입니다. 재설정 완료 후에는 **로그인 화면으로 보내주세요** (자동 로그인 시도 시 `AUTH-002`가 납니다).

## 4. 🟡 인증(SMS) 관련 신규 제약

### 4-1. 비밀번호 정책 신설

**비밀번호를 입력받는 모든 API**에 동일하게 적용됩니다.

| API | 필드 |
| --- | --- |
| `POST /api/auth/signup` | `password` |
| `POST /api/auth/login` | `password` |
| `POST /api/auth/password/reset` | `newPassword` |

> **영문 + 숫자 + 특수문자를 모두 포함한 8~20자**

```
정규식: ^(?=.*[A-Za-z])(?=.*\d)(?=.*[^A-Za-z0-9]).{8,20}$
```

위반 시:
```json
{ "code": "COMMON-002", "message": "비밀번호는 영문, 숫자, 특수문자를 모두 포함한 8~20자여야 합니다." }
```

**가입·로그인·재설정 세 화면 모두 클라이언트에서 동일하게 검사**해 서버 왕복 전에 안내해주세요. 정규식은 위 값을 그대로 쓰시면 됩니다.

> ℹ️ 로그인 화면에서 형식 위반 시 내려오는 코드는 `AUTH-008`(비밀번호 불일치)이 아니라 **`COMMON-002`(잘못된 입력값)** 입니다. 두 분기를 구분해 안내 문구를 다르게 주시면 좋습니다.
> - `COMMON-002` → "비밀번호 형식을 확인해주세요"
> - `AUTH-008` → "비밀번호가 일치하지 않습니다"

> ⚠️ **로컬 테스트 계정 비밀번호가 바뀌었습니다.** `POST /api/auth/test-signup`(local 전용)이 만드는 계정의 비밀번호가 정책을 만족하도록 `testpassword!` → **`testpassword1!`** 로 변경되었습니다. 기존 값으로 로그인하면 `COMMON-002`가 납니다.

### 4-2. 형식 검증 추가

| 필드 | 규칙 | 적용 API |
| --- | --- | --- |
| `phoneNumber` | `^01[0-9]{8,9}$` (하이픈 없이) | signup, login, sms/send, sms/verify, password/* |
| `password` / `newPassword` | 위 §4-1 비밀번호 정책 | signup, **login**, password/reset |
| `code` | `^[0-9]{6}$` | sms/verify, password/reset-sms/verify |
| `name` | 최대 50자 | signup |

위반 시 `400` + `COMMON-002` + 해당 필드 메시지가 내려갑니다.

### 4-3. SMS 발송/검증 제한 (신규 429)

| code | HTTP | 조건 | 메시지 |
| --- | --- | --- | --- |
| `SMS-004` | 429 | 재발송 **60초 쿨다운** | 인증번호는 1분에 한 번만 요청할 수 있습니다. |
| `SMS-005` | 429 | **24시간 내 5회** 초과 | 하루 인증번호 요청 한도를 초과했습니다. |
| `SMS-006` | 429 | 인증번호 **5회 오입력** | 인증번호 입력 횟수를 초과했습니다. 다시 요청해주세요. |

**대응 가이드:**
- **`SMS-004`** → 재전송 버튼을 **60초 카운트다운**으로 비활성화해주세요. 서버 왕복 없이 막는 게 UX상 낫습니다.
- **`SMS-005`** → 24시간 후 재시도 안내. 재전송 버튼 비활성.
- **`SMS-006`** → **인증번호가 폐기된 상태**입니다. 입력 필드를 비우고 **"인증번호 다시 받기" 단계로 되돌려**주세요. 그대로 재입력하면 계속 실패합니다.

> 제한은 **휴대폰 번호 + 목적(가입/재설정)별로 독립**입니다. 가입용 5회를 소진해도 비밀번호 재설정은 별도로 5회 가능합니다.

### 4-4. 인증 토큰 소모 시점 변경 (개선)

`signupToken` / `resetToken`이 **최종 성공 시점에만 소모**되도록 바뀌었습니다.

기존에는 토큰 검증 즉시 삭제해서, 이후 중복 가입 등으로 실패하면 **사용자가 죄 없이 SMS 인증을 처음부터 다시** 해야 했습니다. 이제 가입/재설정이 실제로 커밋된 뒤에만 토큰이 사라집니다.

👉 **`AUTH-007`(이미 가입된 번호) 등으로 실패했을 때 SMS 인증 단계로 되돌릴 필요가 없습니다.** 토큰이 살아있으니(30분) 입력값만 고쳐서 재시도하면 됩니다.

## 5. 🟡 회원 탈퇴 정책 변경 — 완전 삭제

`DELETE /api/users/me`의 동작이 **논리 삭제 → 완전 삭제**로 바뀌었습니다.

### 삭제되는 것
- 계정 정보, 투자 성향(+관심 테마), 잔돈 규칙, 연동 계좌(업비트 키), 보유 종목
- **결제 원장(결제 내역) 전체**
- 로그인 세션 및 서버 캐시

### 클라이언트 영향
- **복구 불가**입니다. 탈퇴 확인 다이얼로그에 이 점을 명확히 안내해주세요.
  > 예: "탈퇴 시 결제 내역을 포함한 모든 데이터가 삭제되며 복구할 수 없습니다."
- **동일 번호로 즉시 재가입 가능**합니다. 대기 기간(쿨다운) 없습니다.
- 재가입 시 **완전히 새 계정**입니다. 과거 포트폴리오·결제 내역은 복원되지 않습니다.

### 폐기된 에러 코드
**`USER-002`("탈퇴한 계정입니다")는 더 이상 발생하지 않습니다.** 분기 코드가 있다면 제거해주세요. (번호는 혼선 방지를 위해 재사용하지 않고 비워둡니다.)

## 6. 참고 — 결제 파이프라인 (변경 없음, 오해 방지용)

문서와 실제 구현이 달랐던 부분이라 명확히 해둡니다. **코드 변경은 없습니다.**

- **자동/수동 매매 모드는 존재하지 않습니다.** `ExecutionMode`, `AUTO`, `MANUAL` 개념 자체가 폐기되었습니다. **모든 매수는 사용자 승인**을 거칩니다.
- **서버에 FCM 등 푸시 발송 인프라가 없습니다.** `POST /api/payments` 응답을 앱이 받아 **로컬 알림**을 띄우는 구조입니다.
- 실제 상태값은 다음 6개입니다:
  `NOT_INVESTED`, `PENDING_PURCHASE`, `PENDING_DEPOSIT`, `PENDING_TRADE`, `INVESTED`, `FAILED`
  (`WAITING_APPROVAL`, `ORDERING`, `CLASSIFYING`, `EXPIRED`는 **존재하지 않습니다**)
- 승인 후 흐름: `PENDING_PURCHASE` → [승인] → 업비트 **원화 입금(2차 인증)** → `PENDING_DEPOSIT` → [3초 폴링] → 매수 주문 → `PENDING_TRADE` → [10초 폴링] → `INVESTED`
- 24시간 미승인 건은 스케줄러가 `NOT_INVESTED`로 정리합니다.
- 승인 후 진행 상황은 `GET /api/payments/{eventId}/stream` (SSE)로 수신합니다. 키 문제 발생 시 `UPBIT_INVALID_KEY` 이벤트가 옵니다.
