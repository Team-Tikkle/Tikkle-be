# 🚀 티끌(Tikkle) 서비스 기획서 (Business & Service Plan)

## 1. 프로젝트 개요 및 배경 (문제 정의 및 솔루션)

* **문제 정의 (Problem):** 자산 관리를 시작하려는 2030 사회초년생들은 투자할 시드머니와 금융 지식이 부족하여 투자를 어려워합니다. 기존 금융 환경은 일상적인 결제 활동과 투자를 철저히 분리해 두었기 때문에, 이들은 투자를 무겁고 특별한 이벤트로 인식하여 시작조차 못 하고 있습니다.
* **솔루션 (Solution):** '티끌(Tikkle)'은 사용자가 일상에서 카드로 결제할 때 발생하는 잔돈을 성향에 맞게 주식이나 ETF에 자동으로 소수점 매수해 주는 마이크로 인베스팅(Micro-investing) 서비스입니다. 일상적인 결제 후 발생하는 자투리 금액을 자동 투자하여 심리적 부담 없이 자연스러운 자산 증식 경험을 제공합니다.

## 2. 타겟 고객 및 핵심 가치 제안 (UVP)

* **메인 타겟:** 자산 관리를 원하지만 시드머니와 금융 지식이 부족해 투자를 두려워하는 사회초년생 (2030 세대).
* **핵심 가치 제안 (Unique Value Proposition):**
    * **소비와 투자의 연결:** 소비하는 과정에서 무의식적으로 자산을 불려 나가는 일상 밀착형 투자 경험을 제공하여 투자의 심리적 장벽을 허뭅니다.
    * **맞춤형 포트폴리오 (AI Proxy):** 단순 분산 투자가 아닌, 사용자의 위험 감수도, 투자 기간, 선호 테마(예: 배당형, 우량주) 등 개별 성향을 완벽히 대변하는 AI 대리인이 맞춤형 종목을 추천 및 매매합니다.
    * **투명한 데이터 시각화:** 결제 카테고리(카페, 편의점 등)와 연동된 소비 패턴을 분석하여, 사용자의 일상 데이터를 시각적으로 제공하고 현명한 소비와 투자의 선순환을 유도합니다.

## 3. 핵심 비즈니스 로직 및 서비스 플로우

* **1단계 (온보딩 및 성향 분석):** 사용자는 최초 진입 시 투자 성향 설문(위험 감수 정도, 단기/장기, 가치/모멘텀 선호도, 관심 테마, 배당/성장 선호도 등)을 진행하고, 잔돈 발생 규칙(예: 1,000원 미만 절사, 10,000원 미만 절사 등)을 설정합니다.
* **2단계 (결제 감지 및 잔돈 산출):** 사용자가 일상에서 **체크카드**로 결제 시, 스마트폰에 수신되는 '결제 승인 알림(KB Pay, 신한 SOL페이 등)'을 백그라운드에서 스크래핑(Push Scraping)하여 서버로 전송합니다. 서버는 결제 금액을 바탕으로 설정된 룰에 따라 투자할 '잔돈'을 산출합니다.
* **3단계 (결제 카테고리 분류):** 수집된 결제 데이터의 가맹점명은 투티어(2-Tier) 구조를 거쳐 카테고리(카페, 편의점, 식당 등)로 초고속 분류됩니다. (이 데이터는 순수 통계 및 시각화 용도로만 활용됩니다.)
* **4단계 (맞춤 종목 선정 및 매매):** 누적된 잔돈은 사용자가 설정한 방식(자동/수동)에 따라 매매가 진행됩니다.
    * **자동 매매:** AI 대리인이 사용자 온보딩 데이터를 기반으로 가장 적합한 종목을 실시간으로 선정하고 즉시 KIS API를 통해 매수(또는 매수 예약)를 실행합니다.
    * **수동 매매:** AI가 추천한 3개의 종목 중 사용자가 24시간 내에 1개를 선택하여 투자 승인을 진행합니다.

## 5. 시스템 및 데이터 아키텍처 (백엔드 코어)

사용자 기기의 백그라운드 구동 특성과 금융 데이터의 정합성, 외부 AI API의 비용 효율성을 모두 충족하기 위해 **'투트랙 보안(Two-Track Security)'** 및 **'2-Tier 비동기 처리 아키텍처'**를 채택한다.

### 5.1. 결제 데이터 수집 정책 (Push Scraping)
* **수집 방식 명확화:** 서버 대 서버의 Webhook 방식이 아닌, 사용자 스마트폰의 Notification Listener를 활용한 **푸시 스크래핑(Push Scraping)** 방식을 사용한다.
* **대상 플랫폼 제한 (체크카드 전용):** 신용카드(누적 금액 표시) 및 은행 앱(단순 이체/출금 혼선) 알림은 수집 대상에서 제외한다. 오직 가맹점명, 결제 금액, **현재 잔액(Balance)**이 명확히 표기되는 **카드사 앱 및 간편결제 앱(KB Pay, 신한 SOL페이, 네이버페이, 카카오페이 등)의 '체크카드 승인 알림'만 화이트리스트로 지정하여 스크래핑**한다.
    * *기획 의도:* 단순 이체나 계좌 간 이동을 결제로 오인하여 투자되는 정합성 오류를 원천 차단하고, 잔돈 적립에 필요한 주계좌 잔액을 사전에 확보하기 위함이다.

### 5.2. 투트랙 인증 및 웹 보안 아키텍처 (Two-Track Auth)
사용자 인터페이스(UI) 요청과 백그라운드 푸시 스크래핑 요청의 인증 통로를 완벽히 분리한다.

```text
[일반 유저 요청] -------> JWT Authentication Filter -------> 컨트롤러 (인가 완료)
[푸시 스크래핑]   -------> JwtFilter 예외(permitAll) -------> HMAC Interceptor (서명 검증)
```

1.  **일반 서비스 API:** 소셜 로그인 후 발급된 JWT(AccessToken/RefreshToken) 체계를 유지한다.
2.  **푸시 스크래핑 수신 API (`POST /api/payments`):** 앱이 백그라운드 또는 종료(Killed) 상태일 때 OS 가용 시간이 극도로 짧으므로, 토큰 재발급(Refresh) 실패로 인한 데이터 유실을 막기 위해 **JWT 필터 대상에서 예외 처리(`permitAll()`)**한다.
3.  **HMAC SHA-256 서명 검증 도입:** 토큰을 대체하여 클라이언트와 서버가 공유하는 고유 `Secret Key`를 기반으로 무결성을 검증한다.
    * 프론트엔드는 요청 바디(JSON)와 현재 타임스탬프를 조합하여 HMAC 서명을 생성 후 HTTP 헤더(`X-Tikkle-Signature`, `X-Tikkle-Timestamp`)에 실어 보낸다.
    * 백엔드는 인터셉터 레이어에서 이를 검증하며, 타임스탬프 오차가 5분을 초과할 경우 Replay Attack으로 간주하여 `401 Unauthorized`로 차단한다. JWT가 없으므로 요청 바디에 서명 위변조가 불가능한 `userId`를 포함하여 사용자를 식별한다.

### 5.3. 결제 수신 및 Fail-Fast 예외 처리 프로세스
결제 내역이 접수되면 시스템 부하와 외부 비용을 최소화하기 위해 **Fail-Fast(조기 종료) 전략**을 수행한다.

```text
푸시 스크래핑 접수 ➔ HMAC 보안 검증 ➔ 잔돈(spare_change) 계산
                          ⬇︎
            [체크카드 현재 잔액 < 발생 잔돈?] ➔ YES ➔ 즉시 FAILED 저장 및 종료 (Fail-Fast)
                          ⬇︎ NO
            1차 방어선: Caffeine 로컬 캐시 조회 (HIT 시 즉시 PENDING 저장)
                          ⬇︎ MISS
            2차 방어선: RabbitMQ 발행 ➔ LLM 비동기 카테고리 분류 ➔ 데이터 적재
```

1.  **잔돈 계산:** 수신된 결제 금액(`amount`)과 유저가 설정한 잔돈 규칙(예: 1,000원 단위 올림)을 기반으로 투자할 잔돈(`spare_change`)을 산출한다.
2.  **잔액 부족 예외 처리 (Fail-Fast):** 스크래핑 데이터에 포함된 체크카드 현재 잔액(`balance`)이 계산된 잔돈(`spare_change`)보다 적을 경우, 주계좌 출금이 불가능한 상황으로 판단한다. 이 경우 무거운 캐시 검색이나 외부 AI API 연동을 진행하지 않고, 즉시 `PaymentStatus.FAILED` (실패 사유: 체크카드 잔액 부족) 상태로 원장에 기록한 뒤 프로세스를 조기 종료한다.

### 5.4. 2-Tier 카테고리 자동 분류 시스템
비용 효율성과 제로 레이턴시(Zero-Latency)를 달성하기 위해 투티어 분류 체계를 구축한다.

* **1차 방어선 (Caffeine Cache + MySQL):** 전체 결제의 80% 이상을 차지하는 주요 프랜차이즈 데이터는 애플리케이션 인메모리 캐시(`Caffeine Cache`)에 Prefix Match(전방 일치) 형태로 적재하여 0.001초 만에 카테고리를 확정하고 `PENDING(접수됨)` 상태로 저장한다.
* **2차 방어선 (RabbitMQ + LLM Structured Output):** 캐시 미스(Cache Miss)가 발생한 생소한 가맹점은 메인 스레드를 블로킹하지 않기 위해 결제 상태를 `CLASSIFYING(분류 중)`으로 두고 메시지 큐(`RabbitMQ`)로 이벤트를 발행한다. 백그라운드 워커가 메시지를 컨슘하여 OpenAI/Gemini API를 호출하고, 구조화된 JSON 응답을 받아 카테고리를 확정 후 캐시와 매핑 테이블을 업데이트한다.
* **AI Fallback 정책:** 외부 LLM API 통신이 3회 이상 타임아웃되거나 장애 발생 시, 시스템 지연을 막기 위해 해당 결제를 '기타(미분류)' 카테고리로 강제 할당하고 프로세스를 안전하게 마친다.

## 6. 향후 고도화 및 비즈니스 모델(BM) 확장 전략

- **Phase 1 (현재 MVP):** 안드로이드 푸시 가로채기와 KIS 모의투자 API를 조합하여 비용 없이 실시간 코어 로직(Event-Driven)의 완성도를 증명합니다.
- **Phase 2 (데이터 수집 고도화):** 앱 설치 이전의 과거 결제 데이터 부재(콜드 스타트) 문제와 OS 배터리 최적화로 인한 푸시 누락 방어를 위해 CODEF 등의 스크래핑 API를 제한적으로 도입하여 데이터를 동기화(Sync)합니다.
- **Phase 3 (B2B 상용화 모델):** 향후 실제 라이선스를 취득하게 될 경우, 증권사와의 제휴 기반 OAuth 2.0 시스템으로 전환하여 사용자 Key 직접 입력 방식의 UX 한계를 극복하고 실전 투자로 확장할 수 있는 유연한 구조를 지향합니다.

## 7. 기대 효과

본 프로젝트는 단순한 아이디어 구현을 넘어, 복잡한 외부 금융 API(한국투자증권 모의투자) 자격 증명을 다중 테넌트(Multi-tenant) 환경에서 안전하게 암호화하고 토큰 생명주기를 통제하는 고도의 시스템 설계 역량을 증명합니다. 사용자는 번거로운 고민 없이 평범한 소비 생활만으로도 자산 증식의 심리적 안정감을 얻으며, 개발팀은 실제 금융권 코어 뱅킹 트랜잭션에 준하는 트래픽 제어 경험을 포트폴리오로 확보할 수 있습니다.
