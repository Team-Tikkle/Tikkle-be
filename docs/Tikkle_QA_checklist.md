# Tikkle 출시 전 QA 체크리스트 v2 (결제 → 코인 매수 파이프라인)

> **목적** — 실제 앱 설치 후 핵심 파이프라인(결제 스크래핑 → 잔돈 정산 → 매수 제안 → 승인 → 업비트 입금·매수 → 체결)을 **모든 분기**에 대해 검증한다.
> **판정 원칙** — 각 케이스마다 **4개 채널**을 동시에 확인한다: ① 앱 화면 ② 알림(로컬/FCM) ③ DB 상태(`PaymentStatus`) ④ 서버 로그.
> **작성 기준** — 코드 실측 (`docs/Tikkle_payment_investment_flow.md`, `Tikkle_requirements.md`, `Tikkle_FE_handoff_payment_recovery.md` 동기화).

## v2에서 달라진 것

1차 QA에서 발견·수정된 버그(백엔드 11건 · 프론트 12건)의 **회귀 케이스**와, 수정 과정에서 새로 들어온 기능의 **신규 케이스**를 추가했다.

- 신규 섹션 3개: **§7 복구·핸드오프(RC)**, **§11 설정 캐시(SC)**, **§12 AI 후보군(AI)**
- 신규 기능 반영: `GET /api/payments/in-progress`, `PaymentViewStatus.IN_PROGRESS`, SSE `CLOSED` 이벤트 + 구독 시 상태 스냅샷, FCM `DEPOSIT_TIMEOUT` 타입(총 7종), 코인 `is_active` 소프트 삭제
- **V-03 삭제** — `lastPaymentDetectedAt` UI가 앱에서 제거되어 검증 대상이 아니게 됨
- 잔돈 규칙 기본값이 `ROUND_UP_10000` → **`PERCENT_10`** 으로 변경됨 (S-07 · S-13 참고)

### 기록 방법

각 표의 **결과 / 확인일 / 비고** 칸을 직접 채우며 진행한다.

| 기호 | 의미 |
| --- | --- |
| ✅ | PASS |
| ❌ | FAIL (비고에 증상·로그 필수) |
| ➖ | 해당 없음 / 이번 회차 제외 |
| (공란) | 미실행 |

ID 옆 배지 — **🔁** 1차 QA에서 고친 버그의 재검증 · **🆕** 이번에 새로 추가된 항목 · **💰** 실제 원화가 움직이는 항목

## ⚠️ 시작 전 반드시 읽을 것

1. **실제 돈이 움직인다.** 승인(approve) 이후는 **케이뱅크 실계좌에서 업비트로 실제 원화 입금 + 실제 시장가 매수**가 일어난다. 최소 주문 5,100원 단위로 **소액 실거래**로 테스트하고, 테스트 계정/카드/업비트 키를 별도로 준비하라.
2. **"아무 일도 안 일어남"이 정상인 케이스가 많다.** 필터에 걸린 결제는 알림도 화면 변화도 없다(§2). 테스터가 "버그"로 오해하기 쉬우니 각 케이스의 "기대 = 무반응"을 명확히 인지하라.
3. **FCM은 보장이 아니라 best-effort다.** 서버는 SSE 전달에 실패한 결과에 대해 FCM 발송을 *시도*할 뿐이고, 토큰 만료·기기 설정·FCM 자체 장애로 도달하지 않을 수 있다. 따라서 **"FCM이 안 왔다"만으로는 버그가 아니다.** 반드시 `GET /api/payments/in-progress`와 결제 내역으로 **최종 상태가 올바르게 수렴하는지**를 함께 본 뒤 판정하라.
4. **로그 확인 명령**
   ```bash
   docker logs tikkle-be --since 5m | grep -E "PaymentService|OrderApproval|UpbitDeposit|UpbitTrade|PushNotification|PendingOrder|SettingsCache|AiPortfolio|CoinSync"
   ```
5. **DB 확인**
   ```sql
   SELECT id, merchant, amount, spare_change, status, reason, created_at
   FROM payment_events ORDER BY id DESC LIMIT 20;
   ```

## 1. 판정 기준 — 매수 제안 알림이 뜨는 "유일한" 조건

로컬 "잔돈으로 투자할까요? 🤔" 알림은 **아래를 전부 통과**할 때만 뜬다. 하나라도 실패하면 **조용히 종료**(알림 없음).

```
서명 유효 → 중복 아님 → 투자 ON → 타겟카드 일치 → 카드 등록됨 → 카테고리 규칙 존재
 → 잔돈 ≥ 5,100원 → 코인 선정 성공  ⇒  PENDING_PURCHASE + 로컬 알림
```

## 2. 결제 수신 · 필터링 (INGEST) — `POST /api/payments`

각 케이스의 **결제를 실제로 발생**시키거나(카드 사용) adb로 주입하여 검증.

| ID | 조건 | 기대 결과 (화면 / 알림 / DB) | 서버 로그 | 결과 | 확인일 | 비고 |
| --- | --- | --- | --- | :---: | --- | --- |
| I-01 | **정상 카드 결제** (잔돈 ≥5,100) | 화면 변화 없음(백그라운드) · 로컬 "매수 제안" 알림 · **원장 insert, PENDING_PURCHASE** | `결제 처리`~`PENDING_PURCHASE` | | | |
| I-02 | **승인취소 알림** ("승인취소 …원") | 없음 / 없음 / **원장 없음** | 없음(앱단 스킵) | | | |
| I-03 | **계좌 출금 알림**(카드 결제 아님) | 없음 / 없음 / 원장 없음 | 없음 | | | |
| I-04 | **서명 위조 / 타임스탬프 5분 초과** | 없음 / 없음 / 원장 없음 | `PAYMENT-001/002` (401) | | | |
| I-05 | **중복 transactionId** (같은 결제 재전송) | 없음 / 없음 / **원장 없음**(중복 차단) | `PAYMENT-009` (409) | | | |
| I-06 | **투자 OFF 상태에서 결제** | 없음 / 없음 / **원장 없음** | `PAYMENT-011` (409) | | | |
| I-07 | **타겟카드와 다른 카드로 결제** | 없음 / 없음 / **원장 없음** | `PAYMENT-008` (409) | | | |
| I-08 | **카드 미등록 상태** | 없음 / 없음 / 원장 없음 | `USER-003` (404) | | | |
| I-09 | **해당 카테고리 규칙 없음** | 없음 / 없음 / 원장 없음 | `USER-005` (404) | | | |

> **핵심 구분**: I-05~I-09(필터/설정 차단)는 **원장에 아무것도 안 남는다**(내역에 안 보임). 반면 §3의 잔돈 미달은 **원장에 NOT_INVESTED로 남는다**(내역에 '미투자'로 보임). 이 차이를 반드시 확인.
>
> **I-01 추가 확인** — 응답의 `actionType`이 **`PENDING_PURCHASE`** 인지 로그로 확인할 것. 안드로이드 리스너가 이 문자열로 알림을 분기하므로, 값이 어긋나면 정상 결제인데도 제안 알림이 통째로 안 뜬다(1차 QA에서 실제로 발생). 상세 검증은 P-05.
>
> **I-09가 예상치 못하게 발생하면** 규칙 자체가 아니라 **설정 캐시 오염**일 수 있다 → §11로.

## 3. 잔돈 계산 · 카테고리 (CALC)

**규칙 = ROUND_UP_10000 기준** 정확한 입력→결과 매핑. (`잔돈 = (10000 - 금액%10000) % 10000`)

| ID | 결제 금액 | 계산 잔돈 | 기대 결과 | 상태(DB) / actionType | 결과 | 확인일 | 비고 |
| --- | --- | --- | --- | --- | :---: | --- | --- |
| C-01 | **4,560원** | 5,440 | 투자 진행 · 로컬 알림 O | PENDING_PURCHASE | | | |
| C-02 | **4,900원** (경계) | **5,100** | 투자 진행(경계 통과) · 알림 O | PENDING_PURCHASE | | | |
| C-03 | **4,901원** (경계) | 5,099 | 미달 무시 · 알림 없음 | **NOT_INVESTED** / `IGNORE_MINIMUM_AMOUNT_UNMET` | | | |
| C-04 | **9,900원** | 100 | 미달 무시 · 알림 없음 | NOT_INVESTED / `IGNORE_MINIMUM_AMOUNT_UNMET` | | | |
| C-05 | **10,000원** (딱 떨어짐) | 0 | 잔돈 0 무시 · 알림 없음 | NOT_INVESTED / `IGNORE_NO_SPARE_CHANGE` | | | |
| C-06 | 신규 가맹점(사전에 없음) | — | Gemini 동기 분류 후 정상 진행 | 로그에 AI 호출 | | | |
| C-07 | AI API 장애 상황 | — | ETC로 폴백, 무중단 | category=ETC | | | |
| C-08 | **카테고리 오분류 교정** `PATCH /api/payments/{id}/category` | — | 내역에서 카테고리 변경됨 | category 변경 | | | |

**검증 포인트**
- C-03/C-04/C-05는 **내역 화면에 '미투자'로 보여야** 한다(원장 insert). 안 보이면 원장 적재 누락.
- C-02(5,100 정확히)가 통과해야 한다. 안 되면 임계 비교 연산자(`<` vs `<=`) 버그.
- C-08 이후 대시보드 그래프 반영은 **V-08**에서 별도 검증.
- 다른 규칙(PERCENT_10 등)을 쓰면 금액이 달라지니 **부록 A** 참고.

**PL-03b 상세 절차** (💰 실거래 1건 필수 — 1차 QA에서 가장 위험했던 버그)

> 배경: 스케줄러 풀 크기가 1이던 시절, `AiPortfolioScheduler`(02:00/14:00, 9개 조합 순차 실행)가 스레드를 점유해 3초 주기 입금 폴링이 통째로 멈췄다. 게다가 **타임아웃 판정이 입금 상태 조회보다 먼저** 있어서, 실제로 도착한 입금이 `TIMEOUT`으로 오판돼 `PENDING_PURCHASE`로 되돌아갔고, 사용자가 재승인하면 **원화가 두 번 입금**되고 첫 입금은 업비트에 방치됐다.

1. 14:00 KST 스케줄러 실행이 시작된 것을 로그로 확인한다 (`[AiPortfolioScheduler]` 시작 로그).
2. 그 구간에 소액 결제 1건을 발생시키고 **승인**한다.
3. 2차 인증을 정상 완료한다.
4. 아래를 모두 확인한다.
   - 입금 폴링 로그가 **`tikkle-sched-*` 스레드**에서 3초 주기로 계속 찍히는가 (AI 작업에 막히지 않음)
   - 도착한 입금이 `TIMEOUT`으로 처리되어 `PENDING_PURCHASE`로 되돌아가지 **않는가**
   - 업비트 입금 내역과 `payment_events.deposit_uuid`를 대조해 **입금이 1건뿐인가**
5. (선택) 되돌아간 상황이 재현되면 재승인해보고 **두 번째 입금이 나가는지** 확인한다. 나간다면 즉시 ❌.

**검증 포인트**
- PL-01 성공 시 **`invested_volume`·`invested_price`가 DB에 채워지고** 포트폴리오에 반영되어야 한다.
- PL-03(타임아웃 복구)은 출시 필수 검증. 210초 대기 후 결제 건이 **다시 승인 가능**해야 하고 원화는 안 빠져야 한다. 앱이 이 건을 내역에서 '취소'로 표시하면 ❌ (`PENDING_PURCHASE` 유지가 정답).
- PL-05는 **"케이뱅크에서 출금된 원화가 업비트에 남아있다"**는 고지가 반드시 떠야 한다(돈 관련).

## 11. 설정 캐시 정합성 (SETTINGS CACHE) 🆕

1차 QA에서 발견된 버그: 설정 변경 시 Redis 해시를 **부분 갱신**해 반쪽짜리 캐시가 만들어졌고, 캐시 완성 여부를 단일 필드 존재로 추정하다 보니 **잔돈 규칙이 없는 것으로 오판**돼 결제가 `USER-005`로 실패했다. 지금은 설정 변경이 **캐시 무효화만** 하고, `SettingsCacheService`가 DB에서 전체를 재구축한다.

**모든 케이스의 전제: 캐시가 비어 있는 상태에서 시작한다.**
```bash
redis-cli DEL user:settings:<userId>
```

## 부록 E — 이번 시트에서 제외한 항목
