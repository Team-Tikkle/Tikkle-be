# 🚀 티끌(Tikkle) 서비스 기획서 (Business & Service Plan)

## 1. 프로젝트 개요 및 배경 (문제 정의 및 솔루션)

* **문제 정의 (Problem):** 자산 관리를 시작하려는 2030 사회초년생들은 투자할 시드머니와 금융 지식이 부족하여 투자를 어려워합니다. 기존 금융 환경은 일상적인 결제 활동과 투자를 철저히 분리해 두었기 때문에, 이들은 투자를 무겁고 특별한 이벤트로 인식하여 시작조차 못 하고 있습니다.
* **솔루션 (Solution):** '티끌(Tikkle)'은 사용자가 일상에서 카드로 결제할 때 발생하는 잔돈을 성향에 맞게 비트코인 등 가상자산(코인)에 자동으로 매수해 주는 마이크로 인베스팅(Micro-investing) 서비스입니다. 일상적인 결제 후 발생하는 자투리 금액을 자동 투자하여 심리적 부담 없이 자연스러운 자산 증식 경험을 제공합니다.

## 2. 타겟 고객 및 핵심 가치 제안 (UVP)

* **메인 타겟:** 자산 관리를 원하지만 시드머니와 금융 지식이 부족해 투자를 두려워하는 사회초년생 (2030 세대).
* **핵심 가치 제안 (Unique Value Proposition):**
    * **소비와 투자의 연결:** 소비하는 과정에서 무의식적으로 자산을 불려 나가는 일상 밀착형 투자 경험을 제공하여 투자의 심리적 장벽을 허뭅니다.
    * **맞춤형 포트폴리오 (AI Proxy):** 단순 분산 투자가 아닌, 사용자의 가상자산 투자 성향 5축 — ① 하락장 방어 심리(RiskTolerance), ② 트렌드 민감도(TrendSensitivity), ③ 관심 코인 테마(CryptoTheme: 레이어1·DeFi·AI·Web3 게이밍·RWA·밈), ④ 포트폴리오 분산도(DiversificationType), ⑤ 밈 코인 수용도(MemeAcceptance) — 를 완벽히 대변하는 AI 대리인이 맞춤형 종목을 추천 및 매매합니다.
    * **투명한 데이터 시각화:** 결제 카테고리(카페, 편의점 등)와 연동된 소비 패턴을 분석하여, 사용자의 일상 데이터를 시각적으로 제공하고 현명한 소비와 투자의 선순환을 유도합니다.

## 3. 핵심 비즈니스 로직 및 서비스 플로우
* **1단계 (결제 감지 및 보안 전송):** 사용자가 일상생활에서 카드로 결제하면, 티끌(Tikkle) 안드로이드 앱이 푸시 알림을 스크래핑하여 가맹점명, 결제 금액 등의 데이터를 파싱합니다. 파싱된 데이터는 탈취(Replay Attack 등) 방지를 위해 HMAC SHA-256 서명 처리되어 백엔드 서버로 전송됩니다.
* **2단계 (조기 차단 및 무결성 검증 - Fail-Fast):** 백엔드 서버는 인입된 푸시 이벤트 데이터의 서명을 검증하고, 고유 transactionId를 통한 중복 결제 검증, 사용자가 지정한 타겟 카드 일치 여부를 즉시 판단하여 무의미한 트래픽을 O(1) 속도로 차단합니다.
* **3단계 (결제 카테고리 분류 및 다이나믹 잔돈 정산):** 보안 검증을 통과한 결제 데이터의 가맹점명은 투티어(2-Tier) 구조(DB 키워드 사전 + 동기 LLM 분류)를 거쳐 7대 카테고리로 초고속 분류됩니다. 분류가 확정된 카테고리에 맞춰 유저가 온보딩 시 개별 설정한 '다이나믹 잔돈 룰(예: 카페는 1만원 올림, 마트는 2만원 올림)'을 적용하여 잔돈을 정산합니다.
* **4단계 (365일 24시간 실시간 맞춤 매매):** 코인 시장은 24시간 연중무휴로 운영되므로, 잔돈 정산이 완료되면 장중/장외 대기 없이 즉각적으로 매매 파이프라인이 가동됩니다. (매매 코인은 결제 시점 실시간 산출이 아닌, 매일 자정 구동되는 '포트폴리오 리밸런싱 스케줄러'가 일자별로 사전 배정한 타겟 코인을 따릅니다.)
    * 자동 매매(AUTO): 원장을 `ORDERING`으로 선전이한 뒤 업비트(Upbit) API로 즉시 매수를 실행하고, 체결 성공 시 `INVESTED`로 확정합니다.
    * 수동 매매(MANUAL): 원장을 `WAITING_APPROVAL`로 저장하고 추천 코인을 유저에게 푸시 알림으로 발송하며, 유저 승인 시점에 매수를 트리거합니다.

## 5. 시스템 및 데이터 아키텍처 (백엔드 코어)

사용자 기기의 백그라운드 구동 특성과 금융 데이터의 정합성, 외부 AI API의 비용 효율성을 모두 충족하기 위해 **'투트랙 보안(Two-Track Security)'** 및 **'2-Tier 비동기 처리 아키텍처'**를 채택한다.

### 5.1. 결제 데이터 수집 정책 (Push Scraping)
* **수집 방식 명확화:** 서버 대 서버의 Webhook 방식이 아닌, 사용자 스마트폰의 Notification Listener를 활용한 **푸시 스크래핑(Push Scraping)** 방식을 사용한다.
* **타겟 카드 지정 및 플랫폼 필터링:** 사용자는 온보딩 시 투자에 활용할 '특정 체크카드(카드사 및 마지막 4자리)'를 지정한다. 클라이언트(안드로이드 네이티브 껍데기)는 기기에 인입되는 알림 중 화이트리스트 카드사 앱(KB Pay, 신한 SOL페이 등)의 푸시만 패키지명(Package Name)으로 1차 필터링한다. 이후 카드사별 정규식(Regex)을 다르게 적용하여 가맹점명, 결제 금액, 결제된 **카드 마지막 4자리**를 파싱하고, 푸시 알림 발생 시간(postTime)을 조합하여 **결정적 해시(Deterministic Hash) 기반의 고유 ID(transactionId)**를 생성하여 백엔드로 전송한다.
    * *기획 의도:* 사용자가 생활비, 데이트 통장 등 목적별로 카드를 분리하여 사용하는 점을 고려하여, 본인이 동의한 특정 카드의 소비 지출에서만 잔돈 투자가 발생하도록 통제권을 부여하기 위함이다. 카드사 푸시 알림의 특성상 실제 계좌 잔액은 누락되는 경우가 많으므로 계좌 잔액 검증은 생략한다.

### 5.2. 투트랙 인증 및 웹 보안 아키텍처 (Two-Track Auth)
사용자 인터페이스(UI) 요청과 백그라운드 푸시 스크래핑 요청의 인증 통로를 완벽히 분리한다.

```text
[일반 유저 요청] -------> JWT Authentication Filter -------> 컨트롤러 (인가 완료)
[푸시 스크래핑]   -------> JwtFilter 예외(permitAll) -------> HMAC Interceptor (서명 검증)
```

1.  **일반 서비스 API:** 소셜 로그인 후 발급된 JWT(AccessToken/RefreshToken) 체계를 유지한다.
2.  **푸시 스크래핑 수신 API (`POST /api/payments`):** 앱이 백그라운드 또는 종료(Killed) 상태일 때 OS 가용 시간이 극도로 짧으므로, 토큰 재발급(Refresh) 실패로 인한 데이터 유실을 막기 위해 **JWT 필터 대상에서 예외 처리(`permitAll()`)**한다.
3.  **HMAC SHA-256 서명 검증 도입:** 토큰을 대체하여 클라이언트와 서버가 공유하는 고유 `Secret Key`를 기반으로 무결성을 검증한다.
    * 프론트엔드는 요청 바디(JSON)와 현재 타임스탬프를 조합하여 HMAC 서명을 생성 후 HTTP 헤더(`X-Tikkle-Signature`, `X-Tikkle-Timestamp`)에 실어 보낸다.
    * 백엔드는 인터셉터 레이어에서 이를 검증하며, 타임스탬프 오차가 5분을 초과할 경우 Replay Attack으로 간주하여 `401 Unauthorized`로 차단한다. JWT가 없으므로 요청 바디에 서명 위변조가 불가능한 `userId`를 포함하여 사용자를 식별한다.

### 5.3. 결제 수신 및 다이나믹 잔돈 정산(Fail-Fast) 프로세스
카테고리별 맞춤 잔돈 규칙을 적용하기 위해, 보안 검증 후 '카테고리 분류'를 선행하고 잔돈을 정산하는 파이프라인을 가동한다.

```
[푸시 스크래핑 접수] ➔ [HMAC 보안 검증]
⬇︎
[1단계 Fail-Fast: 중복 결제 검증 (Redis SETNX → DB 2차 확인)] ➔ YES ➔ 즉시 종료 (Idempotent 리턴)
⬇︎ NO
[2단계 Fail-Fast: 타겟 카드 매칭 (Redis 유저 설정 캐시)] ➔ NO ➔ 즉시 종료 (투자 스킵)
⬇︎ YES
[1차 방어선: payment_category_mapping 키워드 사전 조회 (카테고리 1차 분류)]
 ┣━▶ HIT (카테고리 확정) ➔ 유저 잔돈 규칙 적용 및 계산 ➔ [3단계 0원/최소금액 필터링] ➔ (스킵이면 NOT_INVESTED, 통과면 매수 파이프라인 진입)
 ┗━▶ MISS (생소한 가맹점) ➔ 2차 방어선(동기 AI 분류) 진입
⬇︎
[2차 방어선: 동기 LLM 카테고리 분류 (Google Gemini, 3초 타임아웃)]
 ┣━▶ 분류 성공 ➔ 키워드→카테고리 사전에 결과 누적(UPSERT) ➔ 유저 잔돈 규칙 적용 및 계산 ➔ [3단계 0원/최소금액 필터링] ➔ 매수 파이프라인 진입
 ┗━▶ 분류 실패/타임아웃 ➔ DB 저장 없이 200 OK로 우아하게 조기 종료
```

#### 5.3.1. 3대 Fail-Fast 세부 정책
1. **1단계: 중복 결제 원천 차단 (Idempotency Check):**
   * 프론트엔드가 가맹점명, 결제 금액, 알림 발생 밀리초(postTime)를 조합해 생성한 **결정적 해시 고유 ID(`transactionId`)**를 1차로 **Redis `SETNX`(`payment:tx:{transactionId}`, TTL 24h)**로 검사하여 동시성 환경에서도 O(1)로 중복을 차단한다. 이미 점유된 키이면 후속 트랜잭션(사전 탐색, LLM API 호출, 업비트 매수 등)을 전면 차단하고 즉시 우아하게 종료(Return)한다. 트랜잭션 롤백 시에는 점유 키를 해제하며, DB의 `transaction_id` UNIQUE 제약으로 2차 방어한다.

2. **2단계: 타겟 카드 일치 검증 (Card Matching Check):**
   * 유저가 온보딩 시 등록한 카드 정보(카드사 및 4자리 번호)를 **Redis 유저 설정 캐시(`user:settings:{userId}` Hash)**에서 조회하여 수신 푸시 데이터(`cardCompany`, `cardNumberLast4`)와 대조한다. 캐시가 증발한 경우 DB에서 조회 후 Redis에 재적재(Re-warming)한다. 일치하지 않거나 온보딩 미완료 유저의 결제 건은 비즈니스 연산 및 DB 적재 없이 즉시 프로세스를 종료한다.

3. **3단계: 잔돈 필터링 (Zero & Minimum Spare Change):**
   * 유저 설정 규칙(예: 1만원 단위 올림)을 기반으로 자투리 투자금(`spare_change`)을 계산한다.
   * 잔돈이 `0원`이거나 **최소 투자 금액(5,000원) 미만**일 경우, 투자금은 없으나 사용자의 전체 소비 통계 관리를 위해 **원장에 `NOT_INVESTED(투자안함)` 상태와 사유(`reason`)로 안전하게 저장(Save)한 뒤 후속 매수 트랜잭션을 스킵하고 종료**한다.
   * *기획 의도:* 투자 가치가 없는 트래픽이 매매 파이프라인에 쌓여 업비트 호출/시스템 자원을 낭비하는 것을 방지한다.

**매수 파이프라인 정상 진입:**
   * 무결성 검증, 중복 검증, 잔돈 필터링을 모두 통과한 순수 유효 결제 건에 한해서만 `PaymentEvent` 객체를 빌더로 생성하여 데이터베이스에 적재하고, 유저의 매매 모드에 따라 매매를 제어한다.

#### 5.3.2. 24시간 실시간 매매 및 최종 상태 전이
분류 및 잔돈 계산이 완료된 결제 건은 유저의 매매 모드 설정에 따라 즉각적으로 제어된다. 코인 시장은 24시간 운영되므로 별도의 장외 대기열 로직이 불필요하다.

* **자동 매매 (executionMode: AUTO):** 업비트 API 호출 전 원장 상태를 `ORDERING(주문 중)`으로 선전이하여 원장 불일치를 방어한 뒤, 동기적으로 Upbit 매수를 호출한다. 체결 성공 시 `INVESTED(매수 완료)`, 실패 시 `FAILED(실패)`로 사유와 함께 전환한다.
* **수동 매매 (executionMode: MANUAL):** 즉시 업비트 API를 호출하지 않는다. 원장에 추천 코인을 매핑하여 `WAITING_APPROVAL(승인 대기)` 상태로 저장한 뒤, 유저에게 투자 권유 푸시 알림을 발송하고 프로세스를 종료한다. 추후 유저가 앱에서 승인하는 시점에 Upbit 매수가 트리거되며 성공 시 `INVESTED`로 전환된다. 거절 시 `NOT_INVESTED`로 처리되고, **24시간 내 미승인 건은 매시간 구동되는 만료 스케줄러가 `NOT_INVESTED`로 자동 정리**한다.

### 5.4. 2-Tier 카테고리 자동 분류 시스템
비용 효율성과 제로 레이턴시(Zero-Latency)를 달성하기 위해 투티어 분류 체계를 구축한다. (별도 메시지 큐 인프라 없이 DB 사전 + 동기 LLM 호출로 단순화한다.)

* **1차 방어선 (DB 키워드 사전, `payment_category_mapping`):** 한 번이라도 분류된 가맹점 키워드는 전역 사전 테이블에 누적되어, 부분 일치(`keyword LIKE`) 조회로 카테고리를 즉시 확정한다. 유저 무관 전역 캐시이므로 서비스가 운영될수록 적중률이 상승한다.
* **2차 방어선 (동기 LLM Structured Output, Google Gemini):** 사전 미스(생소한 가맹점)는 Spring AI를 통해 Google Gemini를 **동기 호출(3초 타임아웃)**하여 핵심 상호명(`keyword`)과 7대 카테고리(`category`)를 구조화된 JSON으로 추출한다. 성공 시 결과를 사전 테이블에 UPSERT하여 이후 동일 가맹점은 1차 방어선에서 처리되도록 학습시킨다.
* **AI Fallback 정책:** 외부 LLM 통신이 타임아웃되거나 비정상 응답(필드 누락 등)일 경우, 시스템 지연을 막기 위해 해당 결제를 **DB에 적재하지 않고 `200 OK`로 우아하게 조기 종료**한다(투자 스킵). 클라이언트는 `IGNORE_CLASSIFICATION_FAILED` 액션 타입을 수신한다.

## 6. 향후 고도화 및 비즈니스 모델(BM) 확장 전략

- **Phase 1 (현재 MVP):** 안드로이드 푸시 가로채기와 업비트 API를 조합하여 실시간 코어 로직(Event-Driven)의 완성도를 증명합니다.
- **Phase 2 (데이터 수집 고도화):** 앱 설치 이전의 과거 결제 데이터 부재(콜드 스타트) 문제와 OS 배터리 최적화로 인한 푸시 누락 방어를 위해 CODEF 등의 스크래핑 API를 제한적으로 도입하여 데이터를 동기화(Sync)합니다.
- **Phase 3 (B2B 상용화 모델):** 향후 가상자산 사업자 라이선스 및 거래소 제휴 기반 OAuth 2.0 시스템으로 전환하여 사용자 Key 직접 입력 방식의 UX 한계를 극복하고 서비스를 확장할 수 있는 유연한 구조를 지향합니다.

## 7. 기대 효과

본 프로젝트는 단순한 아이디어 구현을 넘어, 복잡한 외부 금융 API(업비트) 자격 증명을 다중 테넌트(Multi-tenant) 환경에서 안전하게 암호화하고 토큰 생명주기를 통제하는 고도의 시스템 설계 역량을 증명합니다. 사용자는 번거로운 고민 없이 평범한 소비 생활만으로도 자산 증식의 심리적 안정감을 얻으며, 개발팀은 실제 금융권 코어 뱅킹 트랜잭션에 준하는 트래픽 제어 경험을 포트폴리오로 확보할 수 있습니다.
